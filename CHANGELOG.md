## [2.0.3] - 2026-08-18

**Curtain is now signed with a Developer ID and notarized by Apple.** Both the `.dmg` and the
app inside it are signed, notarized and stapled, so Gatekeeper accepts a fresh download with
no workaround and the check succeeds offline. The `xattr -dr com.apple.quarantine` step is
gone for good.

### Added

- **Notarized releases.** `Scripts/release.sh` gained App Store Connect API key support
  (`CURTAIN_NOTARY_KEY` + `CURTAIN_NOTARY_KEY_ID` + `CURTAIN_NOTARY_ISSUER`), tried after a
  notarytool keychain profile and before an Apple ID. This was not a preference: testing the
  stored credentials against Apple found the app-specific password returns `HTTP 401 Invalid
  credentials` while the API key authenticates cleanly, so the only working credential was the
  one the script could not consume. The API key is also the better automation credential, being
  a file plus two identifiers that map onto CI secrets directly and are not bound to an
  individual Apple ID's 2FA state.

### Fixed

- **The `.dmg` itself is now signed, notarized and stapled, not just the app inside it.**
  Stapling only the app left the `.dmg` assessed by Gatekeeper as "rejected — no usable
  signature", which is precisely the warning notarization is supposed to remove: the `.dmg` is
  what the user downloads, so it is what carries the quarantine flag and gets checked first.
  Verified by applying a real download quarantine flag to the built `.dmg` and confirming
  `spctl` reports `accepted / source=Notarized Developer ID` with no workaround applied.
- **The release script no longer prints the ad-hoc quarantine warning after a notarized
  build.** It reported the ad-hoc caveat unconditionally, so a fully clean notarized run still
  ended by telling the maintainer to warn users about a step that no longer applied. The
  summary now reports against what was actually built, and for notarized builds prints the
  app and `.dmg` Gatekeeper assessments plus both stapled tickets.
- **The checksum is now computed after the `.dmg` is signed and stapled.** Both operations
  mutate the file, so hashing earlier would have published a checksum that did not match what
  users download.

### Note for existing users

Upgrading from v2.0.2 or earlier clears Curtain's Accessibility permission once, because macOS
ties that permission to the code signature and this release changes it from ad-hoc to a real
Developer ID. Curtain still shows as armed, so the loss is silent — re-enable it under System
Settings, Privacy & Security, Accessibility, then use "Activate Now" once to confirm the cover
rises. This is a one-time cost: the Developer ID identity is stable, so future updates keep the
permission rather than dropping it on every install, which is what ad-hoc builds did.

### Documentation

- **README now explains that updating Curtain silently drops its Accessibility permission,
  and how to restore it.** Found by installing v2.0.2 over v2.0.0 and testing the result:
  the app came back armed, the bounded "Test Curtain (10s)" cover worked, but "Activate Now"
  silently refused to raise the cover. Cause: releases are ad-hoc signed rather than
  notarized, so macOS has no stable code identity to bind the TCC grant to — a replaced
  bundle reads as a different app and the permission is dropped. Nothing was broken; the
  refusal is the designed safe behavior (Curtain will not raise a cover it cannot guarantee
  it can take down) and it does notify at connect time. But because the default
  "If Accessibility is missing" behavior is "Warn and arm anyway", the menu bar still reads
  as armed in the meantime, so a user who does not know to re-grant can believe they are
  covered when they are not. The README now says to re-grant after each update, how to clear
  a stale entry, and how to verify with "Activate Now"; it also points at the "Refuse to arm"
  option for anyone who would rather fail loudly and early. Documentation only — no behavior
  change, since the mechanism is a macOS consequence of ad-hoc signing rather than a defect.

## [2.0.2] - 2026-08-18

**Maintenance.** No user-facing behavior changes. Fixes a checksum-verification papercut,
removes the last two build warnings, and fixes the real (long-misdiagnosed) cause of the
Bridge test suite's flakiness.

Like v2.0.0 and v2.0.1, this is an ad-hoc-signed build, so the `xattr -dr com.apple.quarantine`
step in the README still applies. Notarization remains available but deliberately unadopted:
for a project this small it adds certificate handling, CI secrets and an annual renewal in
exchange for removing one documented install step.

### Fixed

- **The published `.dmg.sha256` sidecar is now verifiable with `shasum -c`.** It previously
  contained a bare 64-character hash with no filename field, so the standard
  `shasum -a 256 -c Curtain-X.Y.Z.dmg.sha256` invocation failed with "no properly formatted
  SHA checksum lines found". Comparing the hash by eye worked, but a user reaching for the
  standard verb hit a confusing error on a supply-chain verification step, which is the worst
  place to have one. `Scripts/release.sh` now emits the conventional two-field
  `<hash>  <filename>` form, using the basename so it verifies from whatever directory the
  user downloaded both files into rather than naming the build machine's absolute path.
  Affects v1.0.0, v2.0.0 and v2.0.1 identically; those published sidecars are deliberately
  left as-is, since rewriting a published checksum artifact after the fact is worse than the
  papercut it would fix.

- **Fixed the actual cause of `Bridge/tests/test_updater.py`'s long-standing flakiness, which
  was misdiagnosed as a timing problem.** The recorded diagnosis was subprocess timing
  sensitivity under concurrent load, with widened timeouts as the suggested remedy. That
  diagnosis was wrong, and no timeout change fixes it. Every `apply_update` call in this
  module stages a real venv and really pip-installs the package under test; for the tests
  that stage from this repo's own root, that means installing `opencv-python-headless` and
  `numpy` (roughly 150MB of venv) nine times per run, into temp directories pytest retains
  between runs. After a few consecutive runs the disk fills and pip raises a real
  `OSError: [Errno 28] No space left on device`, which then fails whichever assertion the
  test was actually making — hence a different test appearing to fail each time, the pattern
  that made it look like a race. The failing pip error was observed directly rather than
  inferred. Fixed with an autouse fixture that keeps staging genuinely real (a real venv is
  created, a real pip install runs, and validation still imports the staged package, resolves
  its metadata and invokes its `--version` entry point) while removing only the redundant
  re-download of dependencies the test environment already has, via `--system-site-packages`
  and `--no-deps`. Verified with 10 consecutive green runs; peak disk use during the suite
  dropped from 83% to 55% on the same machine.

- **Removed the last two compiler warnings, so a clean release build now emits zero.** Both
  predated the v2.0 work and survived the whole phase. `InputFilter.swift`'s
  `physicalStateIDValue` was a `nonisolated` computed property reading a main-actor-isolated
  stored constant, which warns under Swift 6 isolation checking; it is now a single
  `nonisolated static let`, which is trivially `Sendable` and needs no accessor indirection.
  `Notifier.swift` used `UNUserNotificationCenter.add`'s completion-handler form inside code
  that was already running in an async `@MainActor` context, and now awaits the async
  alternative directly.

### Changed

- Widened `updater.py`'s staging subprocess timeouts (venv creation 30s to 120s, pip install
  120s to 300s). This is unrelated to the test fix above: it reflects that the Bridge runs on
  a Raspberry Pi, where installing this package's dependencies over the Pi's network and SD
  card is genuinely slow, and a too-short timeout there reports a spurious update failure and
  triggers an unnecessary rollback.

## [2.0.1] - 2026-08-16

**Patch release.** Post-release hardening pass on v2.0.0: fixes a critical unauthenticated
LAN attack surface on the KVM Bridge's crash-relay path, closes two Swift test flakes, and
fixes three High-severity Bridge correctness bugs (silent Telegram delete failures, a
degenerate-frame classification bug, and partial password typing on unmappable characters).
No API, schema, or behavior changes for the normal (non-KVM-Bridge) app flow.

### Fixed

- **Fixed a cross-test-isolation race between `SessionMonitorHeartbeatTests` and `MCPServerTests` that could flake `MCPServerTests.testCurtainStatusReturnsKnownState`.** Both files previously read/wrote the exact same real, hardcoded, non-injectable path (`~/Library/Application Support/Curtain/heartbeat.json`) — `SessionMonitorHeartbeatTests` starts real `SessionMonitor` instances whose Timer ticks every ~2s and overwrites that file with a real current timestamp, while `MCPServerTests.testCurtainStatusReturnsKnownState` writes a hardcoded fixture timestamp (`"2026-08-15T12:00:00Z"`) to that same file and asserts the MCP server's `curtain_status` response echoes it back verbatim. Since `swift test` runs every test target in one process by default, a `SessionMonitor` instance from a still-live or not-yet-fully-torn-down `SessionMonitorHeartbeatTests` test could overwrite the shared file between `MCPServerTests`' write and its later read, clobbering the hardcoded expectation with a real current-ish timestamp — this is not a product bug, and it was observed and independently reproduced (2 failures in 5 consecutive `swift test` runs) before the fix. Not merely a timing-margin issue: no wait/timeout widening could have closed this gap, since the race is between two independent processes' worth of state, not a single slow assertion.

  Fixed by adding a genuine injection seam: `SessionMonitor.heartbeatDirectoryOverride` (a `public nonisolated(unsafe) static var URL?`, defaulting to `nil`) and `SessionMonitor.heartbeatDirectory()` (a `public nonisolated static func` resolving to the override when set, otherwise the real `~/Library/Application Support/Curtain` path) — the same static-var seam pattern this codebase already uses for `CaptureProbe.processRunner` and `CrashReportMonitor.readLastHeartbeatTimestamp`. Both the write side (`SessionMonitor.writeHeartbeatFile`) and the read side (`CurtainStatusTool.readHeartbeatTimestamp`, in the `Curtain` target) now resolve the heartbeat directory through this single function, so they can never disagree about where the file lives. `SessionMonitorHeartbeatTests` and `MCPServerTests` each set the override to their own private, per-test-run temp directory in `setUp()` and clear it in `tearDown()`, so the two test files' heartbeat files are now in entirely separate directories and can never collide with each other or with a real running Curtain instance's heartbeat file. Production behavior is unchanged: the override defaults to `nil` and no production call site sets it, so `heartbeatDirectory()` always resolves to the same real Application Support path it did before.

  While reproducing this, also confirmed (and widened) three timing-margin waits in `SessionMonitorHeartbeatTests` that flake under this project's routine heavy concurrent multi-agent build load: `testHeartbeatArmedFieldTracksSettings`' wait for the `armed` field to flip on disk (6s -> 20s, matching the tolerance philosophy already established by this file's own `testHeartbeatWrittenAcrossRealTickCycles` comment), and the two "heartbeat file exists" / "timestamp advanced" waits in `testHeartbeatWrittenAcrossRealTickCycles` and `testHeartbeatOverwritesRatherThanAppends` (5s/6s -> 20s each) — `CaptureProbe`'s own shell-out probes are bounded by a 5s `shellTimeout`, so under heavy swap pressure a single tick's probe queue can itself approach that bound before the first write happens, which is exactly what was observed directly during this fix (a real 12s single-tick duration under ~86% swap usage). These are test-side tolerance widenings only — SessionMonitor's real 2s poll cadence is unchanged.

### Security

- **Fixed an unauthenticated LAN relay path from the KVM Bridge into the FileVault-unlock Telegram chat.** `Bridge/curtain_bridge/crash_relay.py`'s `POST /crash-report` endpoint and `health.py`'s `GET /health` endpoint both bind to `0.0.0.0` by deliberate design (Curtain.app needs direct LAN reachability to them — see `KVMBridgeDeployer.checkHealth`'s doc comment), but neither previously required any credential. Anyone on the same LAN as a deployed TinyPilot Bridge could POST an arbitrary `{"summary": "..."}` to `/crash-report` and have it relayed verbatim, unauthenticated, into the same Telegram chat `TelegramLoginModule` uses for the "Mac rebooted, reply with your password to unlock" recovery flow — since that flow treats any incoming message in the chat as a password reply, a crafted summary could impersonate Curtain's own recovery prompt and trick the user into replying with their real Mac password. Both endpoints now require a shared-secret `Authorization: Bearer <token>` header, checked with a constant-time comparison (`hmac.compare_digest`) and enforced fail-closed — every request is rejected with `401` if no token has ever been provisioned, never silently allowed through. The token is a 256-bit value from `SecRandomCopyBytes` (not `UUID()`, which is not designed as a security token), generated fresh on every deploy and delivered to the Pi over the same SSH channel already used for the Telegram bot token; it is never logged on either side. Provisioning is automatic and silent as part of the setup wizard's deploy step (no new UI, since this is a Curtain-generated secret, not one the human types) — re-running the wizard against an already-deployed Pi (the documented "re-run any time" upgrade path) also provisions the token for installs that predate this requirement. This does not require an internet-facing attacker or zero-click exploit — it requires LAN access plus the user being convinced to reply to a fake prompt — but it was a real path to the Mac's unlock password from anyone who could reach the TinyPilot's network segment, so it is documented here without understatement.

- **Fixed three High-severity findings from a post-release Bridge code review.** `telegram_client.py`'s `TelegramLoginModule._handle_update` now sends the human a follow-up warning if `deleteMessage` fails on their password-reply message, instead of only logging the failure silently — previously a plaintext password could sit undeleted in Telegram chat history with zero signal to the user. `detection.py`'s `_best_match_score` now sanitizes `cv2.matchTemplate`'s result matrix with `np.nan_to_num` (NaN/inf -> `-1.0`, TM_CCOEFF_NORMED's true minimum) before `minMaxLoc`; a near-zero-variance frame (e.g. a solid black/gray frame right after an HDMI lock) could otherwise produce NaN scores that made `detect_state()` fall through to its "unreachable" `AssertionError` every poll cycle instead of cleanly classifying as `NO_MATCH`. `hid_typing.py`'s `_type_password_once` now validates every character of a password against the US-QWERTY keymap before typing any of them, raising a new `_UnsupportedCharacterAtPosition` with zero `send_keystroke` calls made if any character is unmappable — previously an unmappable character partway through a password left a partial, wrong string already typed into the target Mac's password field, contradicting the documented "no partial typing" invariant; the resulting Telegram failure message now also names the 1-indexed character position so a human recovering their own machine can diagnose it without already knowing their password's character set.

## [2.0.0] - 2026-08-15

**Major release.** Covers the full scope of E-01 through E-15: security hardening, the
real signing/notarization pipeline, correctness cleanup, the file-size refactor (module
split into `CurtainCore` + `Curtain`), expanded test coverage, settings hardening,
accessibility, observability, CI/CD, reliability work, and the new KVM Bridge /
Telegram-login / Curtain-for-KVM / MCP-surfaces feature set.

**Hardware-verification status (read before relying on any KVM/Telegram feature below):**
the KVM Bridge, Telegram-recovery-login, Curtain-for-KVM display exclusion, and the
Bridge-side MCP server are **code-complete but hardware-unverified** — every automated
test suite passes (Swift + Bridge Python), but none of it has run against a real TinyPilot
KVM, a live Telegram bot token, or an actual second Mac/monitor in the field. Each
individual entry below that touches this feature set repeats its own specific unverified
claims (SSH deploy to a real Pi, real USB vendor/product ID stability, real HID keystroke
fidelity, real update-in-place behavior, etc.) — treat all of it as pending real-hardware
validation, not as shipped-and-confirmed.

- New `KVMInputFilter.swift`: a second, independent input-filtering subsystem for the KVM's dedicated context, built on IOHIDManager rather than CGEventTap (T-P1-E13-02). `InputFilter`'s existing `sourceStateID`-based classification cannot distinguish a TinyPilot KVM's emulated USB HID device from a person's real keyboard at the desk — both report `sourceStateID == 1` (physical hardware), since device identity is already abstracted away by the time an event reaches a CGEventTap. `KVMInputFilter` operates one layer lower: as each HID device attaches (`IOHIDManagerRegisterDeviceMatchingCallback`, plus an explicit already-attached sweep via `IOHIDManagerCopyDevices` at `activate()` time), it resolves the device's vendor ID, product ID, and (where available) location ID via `IOHIDDeviceGetProperty`, and compares it against a registered identity using the new pure, fully-unit-tested `KVMDeviceIdentity.matches(candidate:)` (`vendorID`/`productID` required exact match; `locationID` optional/advisory — a KVM's port path can shift across reconnects, so its absence or mismatch does not by itself fail the match; documented in `KVMDeviceIdentity`'s doc comment). **Blocking is genuine, not merely observational**: a non-matching device is opened with `IOHIDDeviceOpen(_:kIOHIDOptionsTypeSeizeDevice)`, which Apple documents as establishing exclusive communication that "will prevent the system and other clients from receiving events from the device" — an earlier draft used only an input-*value* callback (detect-and-log, no actual suppression), a real gap caught in CR-C review and fixed before this ticket shipped; `deactivate()` releases (`IOHIDDeviceClose`) every device this filter seized so nothing stays blocked after the KVM context ends. Activation is explicit and narrowly scoped: `isEffectivelyActive` requires both a caller-driven `activate()` and a registered identity, so entering the KVM context before a KVM has ever been paired is a no-op rather than a filter that seizes every HID device in existence; `deactivate()` fully tears down the IOHIDManager registration, not just a flag. `InputFilter.swift` is completely unmodified by this ticket (verified via `git diff --stat`, re-verified after the CR-C fix) — the two mechanisms run independently on separate event pipelines (CGEventTap vs. IOHIDManager) and do not call into each other.

Unlike the other three E-12 tickets, this mechanism runs on the Mac (`Sources/CurtainCore/CrashReportMonitor.swift`), not the Bridge — the Bridge's job ends once the Mac is unlocked and re-locked; it only ever sees pixels, never system logs, so it cannot know WHY a crash/reboot happened. New `Bridge/curtain_bridge/updater.py` implements `apply_update(new_package_path)`: stages a new version into `/opt/curtain-bridge/staged/<timestamp>/venv` (never touching the live install), validates it in isolation (import check, a self-check resolving its own version, and a `curtain-bridge --version` entry-point check — which required adding a `--version` flag to `service.py`'s argparse setup, previously missing entirely despite `KVMBridgeDeployer.checkForUpdate` already depending on it), and only then atomically flips the `/opt/curtain-bridge/venv` symlink and restarts the systemd service, followed by a post-swap `/health` poll to confirm the new version is genuinely serving requests before cleaning up the old staged copy. On ANY failure — staging, validation, post-swap restart, or post-swap health check — the previous install is left untouched or explicitly reverted-and-restarted via `_rollback()`, which never returns a false "rolled back successfully" claim: if the revert symlink flip or the post-revert restart itself also fails, it returns an explicit `MANUAL INTERVENTION REQUIRED` message rather than silently claiming success. **Swift side:** extended `Sources/CurtainCore/KVMBridgeDeployer.swift` (not rewritten) with `checkHealth(host:)` — a direct LAN `URLSession` call to `/health` (deliberately not SSH-tunneled; documented reasoning in the type's doc comment: fewer moving parts, no per-call SSH round-trip cost, matching the Bridge's "still reachable when things are stressed" purpose, with an SSH-tunneled fallback documented but explicitly out of scope for this ticket) parsing the response into a typed `HealthStatus` struct; `compareVersions(local:remote:)` (conservative semantic-version comparison — any unparseable version string is treated as "needs update" rather than silently skipped); and `performUpdateIfNeeded(target:localBridgePath:)`, which orchestrates check-health → compare-versions → conditionally trigger `update()` (T-P1-E11-02's existing SSH deploy path, which drives `updater.py` on the Pi) → re-confirm via a second health check, surfacing the result as a typed `UpdateOutcome` (`.upToDate`, `.updated`, `.failedRolledBack`, `.failed`) so the UI can show "update failed, your Pi's previous version is still running" distinctly from a generic error rather than a bare error string. New Swift tests in `Tests/CurtainCoreTests/KVMBridgeDeployerTests.swift` (14 new cases) cover `compareVersions`' pure logic and `checkHealth`/`performUpdateIfNeeded` against a stubbed `healthURLSession` seam (mirroring the existing `processRunner` injection pattern) — no real network call. `Bridge` pytest: 36/36 passing. `swift build -c release` and `swift test`: 163/163 passing (1 pre-existing documented skip for the gated local-SSH round-trip test, unrelated to this ticket). - Crash-recovery heartbeat file (T-P1-E10-01). `SessionMonitor` already ticks every ~2s via a main-thread `Timer`, but nothing previously wrote that fact anywhere durable — `launchctl list`/`ps` can confirm a PID exists but cannot tell you whether the Timer is actually still firing, whether the probe queue has wedged, or whether the reported state is correct. A hung-but-still-running Curtain is worse than a crashed one: a crash is at least visible (no menu-bar icon, no PID), while a hang leaves every external signal saying "it's fine" while the privacy guarantee has silently stopped being enforced. `SessionMonitor` now writes `~/Library/Application Support/Curtain/heartbeat.json` (following the same Application Support root already used by `CrashSignalHandler`'s crash marker) at the end of every `apply(signals:idle:)` call — i.e. post-tick state, always overwritten in place via `Data.write(to:options:.atomic)`, never appended, so it cannot grow unbounded over weeks of uptime. Fields: `timestamp` (ISO 8601 UTC string), `armed` (`Settings.armed`), `connected`, `idleArmed`, `idleFired` (the monitor's own state). A value-type snapshot is captured on the main actor first, then JSON-encoded and written on the existing `probeQueue` background queue (the same queue `tick()` already uses for probe work), so the write never blocks the 2s tick cadence; any directory-create or file-write failure (disk full, permission race) is caught and silently dropped rather than propagated, since a failed heartbeat write must never crash the tick loop. This file is the documented read-dependency for the future E-14 `curtain_status` MCP tool — do not rename any of the five fields without updating that tool. New `SessionMonitorHeartbeatTests` starts a real `SessionMonitor`, waits across real ~2s tick boundaries (`XCTNSPredicateExpectation`, no fast-forward seam exists for the Timer), and reads the file from disk (never in-memory state) to assert the timestamp advances, the `armed` field tracks a live `Settings.armed` flip, and the file size stays roughly constant across repeated ticks (overwrite, not append). Live-verified: real `heartbeat.json` output inspected via `jq` after a live test run, confirming exactly the five documented fields with a fresh, second-resolution timestamp. - `InputFilter` watchdog circuit breaker + honest `AppDelegate.cleanup()` termination-guarantee doc fix (T-P1-E08-04). (a) Both `InputFilter`'s 1Hz watchdog and its `CGEventTap` callback's tap-disabled recovery path called `ensureActive()` with no cap on retries, so a pathological system state (e.g. some other process repeatedly hammering the event system) would re-enable the tap silently forever with zero user-visible signal, even across an entire session. `InputFilter.swift` now tracks genuine re-enables (only counted when the tap was actually found disabled, never on an ordinary watchdog tick that finds it already enabled) in a rolling window, and trips a circuit breaker at 5 re-enables within 10 seconds — chosen because the 1Hz watchdog alone contributes at most ~10 ticks in that window and the async callback path fires independently, so 5 genuine re-enables that fast is well beyond an isolated, self-resolving timeout/user-input flap. Once tripped, `ensureActive()` stops calling `CGEvent.tapEnable` entirely (a deliberate choice over a slower backoff, documented at the trip site: continuing to hammer a persistently-faulting system adds no value and risks masking the real problem) and posts a user-visible `Notifier.post` banner plus a `Log.error` line, both exactly once per trip (throttled). The breaker self-clears — no manual "retry" action was added — once the tap goes 30 seconds without needing a re-enable, on the theory that the same watchdog tick that would drive a manual retry already observes and clears a resolved condition for free; `stop()` also resets all breaker state so a fresh `start()` never inherits a trip from a prior tap lifetime. (b) `AppDelegate.swift`'s top-of-file doc comment previously claimed `cleanup()` "runs on quit, on SIGTERM, and on terminate" unconditionally. The doc comment (both the top-of-file Constraints block and `cleanup()`'s own doc comment) was rewritten to state precisely which three call sites reach `cleanup()` today — menu-driven `quit()`, `applicationWillTerminate(_:)`, and `main.swift`'s SIGTERM handler — and to explicitly note that SIGKILL and a hard crash bypass `cleanup()` entirely, always uncatchable by definition, matching the same boundary already documented for T-P1-E08-02's crash telemetry. - Crash telemetry (T-P1-E08-02): previously, a crash while the curtain was up left zero diagnosable trail — no `NSSetUncaughtExceptionHandler` and no signal handler existed anywhere in the app, so the process just vanished with no record of why. Two layers now ship, with the coverage boundary between them stated explicitly rather than left implicit. Layer 1 (`AppDelegate.applicationDidFinishLaunching`) registers `NSSetUncaughtExceptionHandler`, logging the exception's name, reason, and call stack via `Log.error` before the process dies — this covers uncaught Objective-C/Cocoa `NSException` throws (an invalid AppKit call, KVO misuse, an invalid-argument exception from a Cocoa API), a real and non-trivial share of macOS app crashes since AppKit itself raises `NSException` internally for programmer errors. Layer 2 (new file `Sources/Curtain/CrashSignalHandler.swift`) registers a minimal handler for `SIGILL`/`SIGTRAP`/`SIGABRT` — the signals the Swift runtime's fatal-trap machinery raises for `fatalError()`, force-unwrap of `nil`, array-index-out-of-bounds, and integer overflow, none of which throw an `NSException` and so aren't caught by Layer 1. The handler writes a short, fixed marker (`CURTAIN CRASH SIG=<n>`) to `~/Library/Application Support/Curtain/last-crash.log` using genuinely async-signal-safe primitives — `withUnsafeTemporaryAllocation` (stack/alloca-backed, not heap) for the message buffer and a raw `UnsafeMutablePointer<Int8>` (captured once at install time, never a Swift `Array`/`String` at signal time) for the log path, since an initial implementation using `[UInt8](repeating:count:)` and `Array(someSequence)` inside the handler body was caught in CR-C review as a real async-signal-safety violation — Swift `Array` is heap-backed and its initializer calls into the allocator, which is unsafe if the crashing signal arrived mid-`malloc`. After writing, the handler restores the signal's default disposition and re-raises it so the process still terminates and macOS still produces its normal crash report exactly as if the handler were never installed — a marker-writer, not a crash suppressor. Coverage is stated precisely, including what's still out of scope: `SIGSEGV` (bad memory access), `SIGBUS` (misaligned/unmapped access), and `SIGFPE` (integer divide-by-zero) are real, distinct native-crash signals **not** registered by this ticket — they are not the same gap as the Swift-trap signals under another name. `SIGKILL` remains always-uncatchable by any process, an OS guarantee neither layer can or tries to close. `Log` (`Sources/CurtainCore/Log.swift`) was made `public` (previously `internal`, invisible outside the `CurtainCore` module) so the executable target's `AppDelegate` can call `Log.error` for Layer 1 — no other behavior change. Verified with standalone smoke tests (not shipped in the repo): a raised `NSException` is caught, logged with the correct name/reason/stack, and the process still terminates; a raised `SIGABRT` is caught, the marker is written to disk, the signal is re-raised, and the process still exits via the signal (exit code 134) exactly as without the handler.

### Security

- Persisted the failed-password-attempt lockout backoff state (`failureCount`, `lockoutUntil`) to `UserDefaults` (T-P1-E06-03), closing a gap where the state lived only in `nonisolated(unsafe) private static var`s and reset for free on any process relaunch — an attacker with physical access who killed the process (`kill -9`, forced crash, or a logout/login cycle) after racking up failed attempts could defeat the exponential backoff entirely by simply relaunching the app. Two new `UserDefaults` keys (`lockout.failureCount`, `lockout.untilTimestamp`, the latter a `TimeIntervalSince1970` `Double` since `UserDefaults` has no native `Date` storage) are deliberately in `UserDefaults`, not Keychain — this is non-secret counters/timestamps, not password material (kept a separate concern from T-P1-E06-01's Keychain-backed hash/salt/algo/iterations, no coupling introduced). `failureCount`/`lockoutUntil` are now computed properties reading/writing straight through `Settings.d` on every access rather than caching in-memory, matching the style of `armed`/`launchAtLogin` elsewhere in `Settings.swift` — this is what makes "resume the correct backoff level on relaunch" fall out for free, since there is no separate in-memory state to go stale: a fresh process's very first read of `isLockedOut`/`backoffRemaining` already reflects whatever was last persisted. `resetFailedAttempts()` now clears the persisted `UserDefaults` keys (`removeObject(forKey:)`), not just in-memory state, so a successful unlock actually clears the lockout on disk too. The backoff algorithm itself (3-attempt grace period, 1s/2s/4s/... exponential escalation, 30s cap) is unchanged — only its durability changed. Neither new key was added to `PreferencesWindow.exportableKeys` — this is runtime security state, not a user preference to export/import. Known limitation, documented in code rather than silently left unaddressed: `backoffRemaining` is computed via `lockoutUntil.timeIntervalSinceNow`, so an attacker who also winds the system clock backward can make an active lockout read as expired early; accepted rather than mitigated, since this is a defense-in-depth measure layered on top of the PBKDF2 hash (not the primary control) and a robust clock-rollback detector was judged disproportionate complexity for a secondary control. Verified via `Tests/CurtainCoreTests/SettingsPasswordTests.swift`: a new test drives 5 failed attempts, then reads `isLockedOut`/`backoffRemaining` fresh (simulating what a relaunched process's first read would see, since there is no separate load-on-launch step to bypass) and confirms the lockout is still reported correctly, then reads the raw persisted `UserDefaults` domain directly to confirm both keys are actually durable on disk; a second new test confirms `resetFailedAttempts()` removes both persisted keys from the raw `UserDefaults` domain, not just from the computed accessors' return values.
- Migrated the PBKDF2-HMAC-SHA256 password hash material (`algo`/`salt`/`iterations`/`hash`, previously `Settings.Key.passwordAlgo`/`passwordSalt`/`passwordIterations`/`passwordHash`) from plain `UserDefaults` into the macOS Keychain (T-P1-E06-01). Previously this material lived in a plain plist under `~/Library/Preferences/`, world-readable to the owning user account — any local process, a second user with file access, or a copied/backed-up plist gave an attacker the derived hash, salt, algo, and iteration count directly, letting them brute-force offline at whatever pace their hardware allows, entirely bypassing the app's own lockout/backoff logic (`Settings.registerFailedAttempt`). All four values are now stored together as one JSON blob under a single `kSecClassGenericPassword` Keychain item (service `com.curtain.password`, account `material`, `kSecAttrAccessibleAfterFirstUnlock`) — a single `SecItemAdd`/`SecItemUpdate` call is all-or-nothing, so there is no window where the fields could be individually partially written. A new schemaVersion-2-to-3 migration (`Settings+Migrations.swift`'s `migratePasswordToKeychain()`) runs once on first launch post-upgrade: it reads any existing `UserDefaults`-stored password material, writes it into Keychain, and only removes the four legacy `UserDefaults` keys once the Keychain write is confirmed successful (verify-then-delete ordering) — a Keychain write failure during migration leaves `UserDefaults` completely untouched and the schema version un-advanced, so the migration safely retries on the next launch instead of ever silently losing a real user's password. `Settings.verify()` also gained a read-time well-formedness check on the Keychain item (all fields present/non-empty, with `iterations` required only for the `pbkdf2` algo since the legacy `legacy-sha256` algo never had one): a corrupted/partial Keychain item now falls back to the documented `"curtain"` anti-lockout password with a diagnostic log line, instead of a confusing `verify()` failure. Scope is narrowly the four password fields — every other `Settings` preference remains in `UserDefaults` unchanged, and `PreferencesWindow.exportableKeys`/`OnboardingWindow`'s `setPassword` call site both needed no changes. Verified via `Tests/CurtainCoreTests/SettingsPasswordTests.swift` (now Keychain-backed via an isolated per-test-run `Settings.keychainService` seam mirroring the existing `Settings.d` UserDefaults-suite seam): fresh-install round-trip stores nothing under `password.*` in `UserDefaults`, upgrade-migration carries a seeded legacy password through to Keychain with the original plaintext still verifying afterward and the legacy keys gone, a simulated Keychain write failure during migration leaves the seeded `UserDefaults` values intact and retries successfully once the (simulated) failure clears, and both corrupt/undecodable Keychain-item cases fall back to the anti-lockout password rather than failing confusingly.
- Closed a privilege-escalation gap in the sudoers-fallback disconnect helper (ad-hoc/local installs only; the notarized `SMAppService.daemon` path is unaffected). Previously, the installed NOPASSWD sudoers rule let any local process running as the same user invoke `sudo -n /usr/local/bin/curtain-endsession` directly, bypassing Curtain's own XPC trust check. The installed script now requires a one-time, single-use handshake token written by Curtain immediately before each legitimate invocation; a bare `sudo -n` call with no fresh token present is a no-op. Residual risk: a same-user attacker polling the fixed token path could in principle win a tight race against the sub-5-second-lived token — not a cryptographic guarantee, but a substantial improvement over the prior unbounded-time exploit. Full closure requires the notarized daemon path (tracked separately).
- Closed a PID-reuse TOCTOU race in `CurtainHelper`'s XPC caller check (`isTrustedCaller`). The daemon previously resolved the connecting client's `SecCode` via `kSecGuestAttributePid`, keyed on `NSXPCConnection.processIdentifier` — a reusable integer that, in principle, a different (and potentially hostile) process could occupy between the kernel reporting it and the lookup running. It now resolves the caller via `kSecGuestAttributeAudit`, keyed on the connection's kernel-issued audit token (obtained through the Objective-C runtime, since `NSXPCConnection` does not publish an audit-token accessor in its public header but implements one internally) — an immutable, connection-scoped identity snapshot that cannot be raced the same way. Team-ID pinning and the ad-hoc-build identifier+anchor relaxation (logged loudly) are unchanged. Verified end-to-end with a compiled XPC smoke test: a legitimate caller is accepted and can complete a round-trip call, and a rejected caller never receives a service reply. Accepted risk, unchanged by this fix: the ad-hoc-build relaxation path remains a soft/forgeable binding until Developer-ID signing lands (tracked separately), since there is no Team ID to pin against on an unsigned build.
- Hardened `CurtainHelper`'s screen-sharing disconnect (`DisconnectService.endScreenSharingSession`), which runs as root. It previously used `pkill -f "ScreenSharingSubscriber"` and `pkill -f "RemoteManagement.*[Ss]creen"` — regex matches against the full command line of every process on the system — meaning an attacker-controlled process could craft its own argv to be killed by, or evade, the pattern. Both `-f` (full-argv) patterns are replaced with exact-executable-path targeting: every running PID is enumerated via `sysctl(KERN_PROC_ALL)`, each candidate's real executable path is resolved with `proc_pidpath`, and only a PID whose resolved path exactly matches a known fixed system location (`ScreenSharingSubscriber.xpc`, `RemoteManagementAgent`, `ScreensharingAgent.bundle`) is signalled directly via `kill(2)` — argv content is never consulted. `pkill -x screensharingd` (exact process-name match, not full-argv) is unchanged. Each terminated PID is now logged with its resolved path for auditability. Verified adversarially: a decoy process with `argv[0]` renamed to `ScreenSharingSubscriber_evil` (real executable `/bin/cat`) matched the old `pkill -f` pattern but is correctly rejected by the new exact-path check, while the legitimate `ScreenSharingSubscriber` process is still matched and killed.
- Hardened `DisconnectClient.runAdminShell`, the helper that runs a shell command once with administrator privileges via `osascript`. Audit: neither current call site (`installSudoersHelper`, `removeSudoersHelper`) interpolates untrusted or user-controlled data into the command string — only fixed path constants and base64-encoded (inherently shell-safe) content — so no injection is reachable today. The construction was nonetheless fragile: the command was embedded directly into AppleScript source text via manual backslash/quote `.replacingOccurrences` escaping, a landmine for any future refactor that interpolates variable data without realizing the AppleScript-embedding hazard. Replaced with a fixed, static `on run argv` AppleScript body piped to `osascript` via stdin, with the command passed as a plain process argument rather than interpolated into script text — eliminating AppleScript-string-escaping as an attack surface entirely, since the command can never become part of source text parsed as AppleScript syntax. Verified adversarially: content containing quotes and a `do shell script` fragment designed to break out into a second AppleScript statement is correctly treated as inert shell-command text and cannot execute as additional AppleScript.
- Closed a silent-settings-corruption gap in `PreferencesWindow.importSettings()`. Previously any user-chosen JSON file was decoded via `AnyCodable` and written straight into `UserDefaults` with only a key-name membership check against `exportableKeys` — no type, enum, or range validation on the values themselves. A crafted or corrupted file (e.g. `"onUnlock.action": "garbage"`) silently wrote a nonsense string that then evaluated to `false` everywhere it was read (`Settings.unlockDisconnect`), defeating a security-relevant preference with no error ever surfaced. `importSettings()` now validates every key in `exportableKeys` against an explicit type/enum/range rule (enum sets and numeric ranges cross-referenced against `Settings.swift`'s documented accepted values and `clamp()` bounds) before any write happens; a single invalid key rejects the entire import (zero `UserDefaults` writes) with a clear per-key error message — no partial-apply. Separately, an import that changes the security-relevant per-display cover policy (`displayLinkUUIDs`, `perDisplayCoverDisabled`) from its current value now shows an explicit confirmation alert naming the affected displays before anything is written; Cancel aborts with zero writes. Deliberately no cryptographic signature or checksum was added: a signing scheme would need key generation, secure storage, and a verification pipeline — key-management complexity disproportionate to this app's actual threat model (a single-user Mac importing a local file, not a networked or multi-tenant trust boundary). A human-reviewed confirmation showing exactly what per-display behavior is about to change addresses the real risk (silent, invisible changes to physical-security-relevant settings) at a fraction of the cost, and puts the review burden on the person who can actually judge it — the user looking at their own displays.
- Structured-logging cleanup for security-relevant refusals and rejections (T-P1-E08-01). `CurtainHelper/main.swift`'s `ListenerDelegate.isTrustedCaller`/`shouldAcceptNewConnection` previously logged every connection-rejection and the ad-hoc-relaxation warning via bare `NSLog`, with no subsystem/category and no consistent severity — invisible to a `log stream --predicate 'subsystem == "io.acamarata.curtain"'` filter. Since CurtainHelper is a separate SPM executable target that cannot import `CurtainCore.Log` across the module boundary, it gained its own minimal, self-contained `HelperLog` (`os.Logger`, subsystem `io.acamarata.curtain`, category `"helper"` — distinct from the app's `"curtain"` category); all four rejection/warning call sites in the accept path now use it at `.error`/`.warning` level instead of bare `NSLog`. Separately, `SessionCoordinator.enterActive`'s Accessibility-refusal log and `setArmed`'s arming-refusal log, plus `DisconnectClient.notifyHelperNeeded`'s helper-not-enabled log, were reclassified from the diagnostics-gated `Log.event` to the always-visible `Log.error` — these are refusals of a security-relevant action (the cover failing to arm/activate, or a disconnect request silently doing nothing) that should be visible by default, not hidden behind a toggle nobody has turned on; the redundant direct `NSLog` duplicate at `enterActive`'s Accessibility-refusal site was removed now that `Log.error` covers it unconditionally. Finally, `Log.event`/`Log.error` gained an optional `episode` parameter, and `SessionMonitor` now generates a short per-connect correlation token (`String(UUID().uuidString.prefix(8))`) when a connect is first detected, threading it through `onConnect` to `SessionCoordinator` so a session's connect/idle/end/unlock log lines can be filtered together in Console.app/`log stream`. CurtainHelper's own XPC-side logs do not carry this token — threading it through the `CurtainDisconnectXPC` protocol was judged too invasive for this ticket's scope; this is documented as a known limitation in `DisconnectClient.callHelper()`'s doc comment, so helper-side log lines are correlated to an app-side episode only by timestamp proximity.

## [1.0.0] - 2026-06-10

First public release. Curtain is a menu-bar app for the host side of macOS
Screen Sharing: when a remote session is active it covers every display and
blocks physical input at the desk, so the screen you control remotely stays
private from anyone sitting in front of the Mac.

### Added
- Cover all displays and block desk keyboard and mouse while a remote Screen
  Sharing session is active, after an optional connect grace delay.
- Session detection on three independent signals: the `CGSSessionScreenIsCaptured`
  capture key (primary, transport-independent), an ESTABLISHED inbound TCP
  connection on port 5900 (standard Screen Sharing), and a peered UDP socket on
  5900-5902 (High-Performance Screen Sharing). Process presence and idle listen
  sockets never trigger activation, so an enabled-but-idle Mac is never covered.
- Desk password to reveal the screen, with a built-in `curtain` fallback so the
  Mac is never permanently locked. Password is stored as a salted
  PBKDF2-HMAC-SHA256 hash with attempt backoff.
- Idle actions: when the remote operator goes idle for a configurable time, run
  any of disconnect, lock, displays off, deactivate.
- End-of-session actions: when the remote session ends, run any of lock,
  displays off, deactivate.
- Cover styles: solid color, message, blur, logo, and an aerial video that
  shares one decoder across all displays. Optional clock overlay.
- Per-display cover control: choose all displays or per-display toggles, mark
  DisplayLink monitors, and place the password box on a specific display.
- Optional privileged helper to disconnect the remote session, off by default
  and installed only on explicit opt-in.
- Open at login via `SMAppService`, optional menu-bar item, and a first-run
  onboarding flow.
- Emergency escape: Control + Option + Command + U force-deactivates the curtain
  without Accessibility. When Accessibility is not granted, Curtain refuses to
  cover rather than putting up a screen it cannot unlock.
- Diagnostic probe (`Scripts/probe-detection.swift`) that prints every raw
  detection signal once per second and diffs the full CGSession dictionary.

### Known limitations
- Ad-hoc signed, not notarized. macOS Gatekeeper warns on first launch; clear
  the quarantine flag once with
  `xattr -dr com.apple.quarantine /Applications/Curtain.app`.
- The capture-key and High-Performance UDP detection paths are verified by unit
  tests and on-device probes but not yet against a second physical Mac. Standard
  (TCP) Screen Sharing detection is verified end-to-end.
- The physical-versus-remote input split is a convenience filter, not a security
  boundary. Curtain hides your screen from someone at the desk; it is not a
  defense against local malware.
